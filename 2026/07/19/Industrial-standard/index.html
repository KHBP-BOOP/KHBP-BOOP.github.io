GPU Kernel Benchmark

1. 硬件状态锁定与环境控制（消除噪音）

工业级测试对可复现性（Reproducibility）要求极高。现代 GPU 的自动睿频（GPU Boost）会根据温度动态调整核心频率，这会导致同一段代码在开头和结尾跑出不同的成绩。

  • 锁定 GPU 频率： 在测试前，必须使用命令行工具将 GPU 的核心频率和显存频率锁定在固定值。
  • L2 缓存冲刷（Cache Flushing）： 在多次循环测试中，后一次迭代往往会直接命中 GPU 的 L2 缓存。如果你想评估的是真正的“全局显存（Global Memory）”带宽，需要在每次 Kernel 启动前手动刷新 L2 缓存（通常通过读取一块和 L2 大小相同的哑巴数据来实现）。

2. 自动化多维参数网格搜索（Parameter Sweeping）

工业级 benchmark 绝不会只测一个固定的 Size 或 BlockSize，而是通过自动化脚本或 C++ 模板进行多维矩阵测试。

  • 数据规模（Data Size）： 覆盖从小数据量（受限于 Kernel 启动开销）到大数据量（显卡饱和）的对数级区间（如 $2^{10}$ 到 $2^{28}$）。
  • 执行配置（Execution Configuration）： 自动遍历 BlockSize（从 32、64、128 到 1024），寻找当前硬件架构下占用率（Occupancy）和吞吐量的最佳平衡点。
  • 数据类型（Data Types）： 同时支持 FP32、FP16、BF16、INT8 等，方便在混合精度场景下做横向对比。

3. 统计学严谨性（拒绝单一平均值）

单纯的“总时间 / 迭代次数”容易掩盖异常值（Outliers）。工业级测试通常会引入标准统计指标：

  • 舍弃前几次成绩： 丢弃前 N 次（Warm-up）的耗时。
  • 计算百分位数（Percentiles）： 报告 P50（中位数）、P95、P99（尾部延迟） 以及标准差（Standard Deviation）。如果标准差过大，说明测试环境有严重的系统级干扰（如 CPU 中断或内存抖动）。

4. 健壮的错误处理与异步检查

在之前的简单代码中，我们只处理了同步结果。工业级框架必须拦截所有潜在的异步错误，防止测试进入死循环或输出伪造的零耗时。

5. 高级内存模型与流管理

  • 固定内存（Pinned Memory）： 主机端应当使用 cudaHostAlloc 分配页锁定内存，这样能跑出真实的 cudaMemcpy 极限带宽（通常比普通的 malloc/std::vector 快一倍）。
  • 多流并发（CUDA Streams）： 测试 Kernel 在多任务并行（Compute/Copy Overlap）状态下的表现。
  • 对齐检查（Alignment）： 确保传入 Kernel 的指针对齐到 128 字节，以启用合并内存访问（Coalesced Access）。

6. 工具链打通（NVTX & Roofline 模型）

真正决定核心优化方向的不是那串毫秒数，而是硬件利用率指标。工业级测试代码内部会深度集成 Nsight 工具链。

  • NVTX（NVIDIA Tools Extension）标记： 用代码明确圈出测试的核心区间，在 Nsight Systems 的时间线上可以一目了然地看到对应的波形。

  • SOL（Speed of Light）： 你的代码到底达到了显卡理论计算极限（Compute SOL）或理论带宽极限（Memory SOL）的百分之多少。
  • Bank Conflicts： 针对当前的 Tree Reduction 算法，Shared Memory 的 Bank 冲突次数是多少（查看 sm__sass_data_bytes_mem_shared 相关指标）。

工业界成熟轮子推荐：
如果你要在公司或研究中构建大规模的 GPU 基准测试，不建议完全从零手写这个框架。可以参考 Google Benchmark（原生支持 CUDA 计时与参数 Sweep）或者 NVIDIA 官方的 CUTLASS Profiler 架构，它们是目前工业界标准的测试范式。
