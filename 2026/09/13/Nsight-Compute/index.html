一个函数在给定的计算平台上的性能通常被三个因素限制
内存带宽 数学计算带宽 延迟

大多数情况下，合并访问针对全局内存而言。
在现代profiler术语中，uncoalesced shared accesses可被理解为probably bank-conflicted；excessive wavefronts意为超额的内存事务，其中wavefronts为memory transaction的另一种说法，同时，该偏正短语含义为：本次内存请求导致了多于*所需最小wavefront数量（通常为1至2个）*的wavefront数

关键指标

wave per SM
如果总 block 数量刚好能被一个完整 wave 的容量大小整除，那么波数是整数；否则就会出现小数或非整数波数，表示存在 partial wave，导致尾部效应tail effect，同时这通常意味着GPU资源利用率的下降，对于执行时间较短的kernel的影响尤其明显

流多处理器效率（SM Efficiency）

每线程的寄存器文件占用量是影响sm occupancy的重要因素。oc高不代表性能一定高，但oc过低总代表较弱的隐藏延迟的能力

warp scheduler的issue activity低于20% 可能原因：
sm无待处理数据（内存带宽不足、occu过低）、sm执行单元满负载、等待同步

Roofline Chart

性能 (FLOP/s) = 算术强度 (FLOP/byte) × 内存带宽 (byte/s)
log y = log a + log x

  • 故Roofline图中内存瓶颈部分表现为斜率为1、截距为带宽值对数的一次函数
    斜线的截距（也就是在纵轴上的高低位置）直接由带宽大小决定

算法的算术强度、性能都是可变值，优化步骤：

  1. 消除内存瓶颈：通过分块、融合等手段提高算术强度，向右跨过拐点
  2. 消除计算瓶颈：在计算受限区，优化代码的并行性和指令流水线，让任务点向上移动贴近水平线

Warp State Statistics 指标含义

  • Warp Cycles Per Issued Instruction [cycle]
    warp scheduler每发射一条指令，平均一个warp活跃的cycle数。

    每次发射指令时，warp scheduler从eligible warps中选择一个warp，发射一条或多条指令，该eligible warp变为issued warp

  • Avg. Active Threads Per Warp
    每个warp中，执行了某条指令的thread的数量/占比
    以.ratio为后缀时，数值以绝对值表示，如32
    以.pct为后缀时，数值以百分比表示，如100%

  • Warp State (All Cycles) 图表
    当warp scheduler无法在每个cycle中都发射指令时，应借助该图表排查原因
    反映了warp stall时各类原因的占比情况，各项对应的值相加后等于Warp Cycles Per Issued Instruction [cycle]的值

Scheduler Statistics 指标含义

  • No Eligible [%]
    smsp中的warp scheduler未找到可发射指令时的活跃周期数 的占比

  • One or More Eligible [%]（与Issued Warp Per Scheduler指标采用同一个基础计数器，有效位上的数字一致）
    smsp中的warp scheduler发射一条或多条指令时的活跃周期数 的占比
    通常可以理解为issue slot的利用率，过低通常意味着延迟隐藏不佳

  • Active Warps Per Scheduler [warp]
    每个活跃周期中，smsp上active warps的平均数量

  • Issued Warp Per Scheduler（与One or More Eligible指标采用同一个基础计数器，有效位上的数字一致）
    每个活跃周期中，smsp中的warp scheduler发射指令的平均数量（取值范围0 ~ 1，因为每个smsp每cycle最多发射一条指令）

kernel replay

保存GPU memory中kernel可被访问的部分的backup；
第一次replay pass后，确定实际被写入的部分，即subset；
之后的每次replay pass，只需将subset restore回原始位置

  • 为什么需要replay？
    单次 pass 能同时采集的硬件性能计数器有限，需要通过多个 replay pass 分批采集不同的 metrics，最终组合成完整的分析结果
  • 每次 replay pass 都需要先恢复 subset？
    使 kernel 每次执行时看到相同的内存初始状态，从而保证不同 pass 获取的 profiling metrics 可以对应到同一次 kernel 执行条件

port端口

GPU 中的很多单元（例如缓存、存储单元、SM 内部某些模块等）会用一个公共的数据端口来同时处理输入流量和输出流量，读和写、进和出可能共用同一个物理端口，而不是各自独立拥有端口。共享这个端口的各条“链路”（可以理解为某一种流量、某一个方向、某一个子通道）单独看，可能利用率都不高，远没有达到它们各自的峰值带宽；但是，所有这些链路加在一起的总流量，可能已经把这个共享端口的峰值带宽用满了

当 NCU 显示某个单元的数据端口利用率已经接近峰值时，即使各个子链路利用率不高，也不能认为没有瓶颈，需要关注的是端口级别的聚合带宽，而不是某一条热点链路的单路带宽
优化方向应该是降低该端口的总流量，例如减少不必要的读写、改善数据复用、调整访问模式以减少对同一端口的争用。

计算分诊指南

自顶向下的关于CUDA kernel性能分析问题的工作流，针对于在NVIDIA GPUs上使用Nsight compute进行分析工作的场景。

迭代优化方案

  1. 多个kernel待优化且优先级未定时，首先使用nsys
  2. 不要孤立地根据某个指标进行优化
  3. 每次优化只修改一个导致了性能瓶颈的点
  4. 调整代码后立即重新进行性能分析，判断优化效果
  5. SOL% 表示资源利用率，应该使用内核绝对执行时间衡量性能优劣
  • SOL即理论峰值吞吐量（可以是kernel执行期间的、活跃期间的等等）

d1. 工作负载是否过小？
waves per SM 是否小于1?
block_size是否不是32（一个warp中线程的数量）的倍数？
block_size是否过小？每个SM的block槽位有限。负载相同情况下，block尺寸过小会导致SM上SMEM、寄存器文件等资源的浪费
除非工作负载主要由Tensor Core主导，或计算SOL很高，或内存SOL很高，否则当实际占用率低于60%时，工作负载过小，原因是grid并行性不足。

  1. 比较SM的计算利用率和内存利用率

    • 二者均小于80%

      sm中的某条或某几条管线负载过大。
    • 内存利用率大于80%，计算利用率比起前者低超过15%-20%
    • 二者均大于80%

  2. 当Memory Throughput高但DRAM Throughput低时，检查profile期间的：system地址窗口和peer地址窗口的流量情况、PCIE总线上是否有大量数据传输，以此排查可能存在的频繁地从system/peer内存中访问数据的情况

    System aperture ：GPU地址空间中用于访问系统内存的窗口
    Peer aperture ：GPU地址空间中用于访问另一GPU的显存的窗口
    Aperture traffic ：经过上述窗口产生的数据传输量
