合并访问:

核心原则：让 Warp 内的连续线程访问连续的内存地址。

GPU 以 32B/64B/128B 的粒度从全局内存取数据（一次”事务”），如果一个Warp内32个线程访问的地址连续，一次事务就能满足warp的全部线程

L1/L2 cache

物理内存模型：一维紧密排列。内存不在意Cache Line，只按字节顺序输出。

逻辑内存模型（CUDA编程视角）：一维线性空间（全局内存地址连续）

Cache硬件结构：类似于二维数组（行=Cache Line索引，列=Sector编号）。硬件负责将内存中一维连续（或分散）的数据，映射并填充到这个二维的缓存结构中。

访问GMEM时，配置为不经过L1 cache：
内存事务的粒度、缓存行字节数大小变为32B，对于相对scattered的访问场景，可减少过度读取over-fetch，防止带宽利用率过低
配置为经过L1 cache：
内存事务的粒度、缓存行字节数大小变为128B，对于合并访问相对良好的访问场景，可显著提升带宽
同时，可根据kernel对SMEM的依赖程度，配置L1 cache是否参与数据传输，以此平衡SMEM与L1 cache对每SM上SRAM芯片的占用

Shared Local Memory

位于SM芯片上

MIO throttle stall

全称Memory Input/Output throttle stall，定义：Warp正在等待直到MIO（内存输入/输出）指令队列不再处于满状态。

  • 当一个Warp想要发射一条需要由MIO（内存输入/输出）单元执行的指令，但该单元的指令队列已满，无法接收新指令时，这个Warp就会停滞，报告为MIO Throttle。

  • MIO是NVIDIA SM（流多处理器）中的一个分区，包含多个执行单元。其指令队列及对应的执行单元主要包括：
    1.mio_throttle: 地址计算单元(ADU)、一致性总线单元(CBU)、加载存储单元(LSU)、以及执行特殊数学指令的单元(XU)。
    2.lg_throttle: 同样是LSU，但这是一个更精细的计数器。当MIO队列中本地(Local)和全局(Global)内存指令达到一定水位时，会单独报告为LG Throttle，以优先保证共享内存指令的发射。
    3.tex_throttle: 纹理单元(TEX)的队列满了会单独报告。

产生原因：根本原因是MIO流水线（Pipelines）被过度利用。具体来说，以下操作类型如果过于密集，都可能导致MIO队列堵塞：
内存访问频繁，存取指令过多、
特殊数学指令过多、
Kernel使用的寄存器超出硬件限制，编译器将数据“溢出”到本地内存，显著增加L1缓存和内存I/O的流量，从而加剧MIO队列的压力

Bank Conflict 存储体冲突

共享内存被划分为多个（现代Volta、Turing、Ampere架构中为32个，与 Warp 大小一致）Bank，每个 Bank 宽 4 Bytes（32 bits），连续的 4 Byte 字被分配到连续的 Bank。
每个时钟周期，每个 Bank 只能服务一次读或写请求。如果同一个 Warp 中有多个线程访问同一个 Bank 的不同地址，这些访问必须串行化，直到请求该 Bank 数据的每个线程都已成功获取数据。

从程序员视角判断 bank conflict 时，分析的基本单位是一个 warp（32 个线程）

多个warp的执行是分时调度的；一个warp的一次共享内存请求通常被拆分为一个或多个事务，同一warp的多个memory transaction的执行是流水线式串行执行的；
所以不同warp之间访问同一bank、同一warp不同memory transaction之间访问同一bank均不会造成bank conflict。
Bank conflict是否会发生，在单个memory transaction内部判定。
当一个 warp 使用 float4 访问 shared memory 时，由于单线程访问宽度为16B，硬件可能将一个warp请求拆分成多个transaction（例如每个128B transaction包含8个线程）。此时需要分别检查每个transaction内部线程访问的bank分布，而不是直接按整个warp判断。

Ampere架构前，bank conflict可能发生在LDS/STS指令执行期间、共享内存原子操作中，Ampere架构后，也有可能发生在cp.async/LDGSTS写入共享内存的那一步中

地址 03: Bank 0
地址 47: Bank 1
地址 811: Bank 2
…
地址 124127: Bank 31
地址 128~131: Bank 0 （循环）
…

优化方案

  1. Padding（填充列）

  2. Swizzling（地址异或混淆）

注：每一个 Bank 在一个时钟周期内只能处理一个地址的请求
broadcast 属于 两个或多个线程访问SMEM中同一bank的**同一个32位对齐的地址（word）**地址 的情况
广播机制主要针对读取操作。多个线程同时写入共享内存的同一个位置是未定义行为

Bank conflict 只发生在 Shared Memory 被多个线程并行访问时，包括 global memory → SMEM 的写入以及 SMEM → register 的读取等；global memory、register 本身的访问不会产生 CUDA 所说的 bank conflict。

用户管理的Shared Memory 与 L1/TEX Cache 底层上共用一块物理内存
L1 data cache、shared data cache、Texture data cache are one and the same.

寄存器文件与局部内存

kernel 中的局部变量默认分配在寄存器，单个线程用的寄存器越多，sm上能并行执行的warp就越少（即occupancy会下降）；如占用数量超过寄存器数量，则会溢出至局部内存（位于GPU全局内存上），速度骤降

实际应用中，先保证没有寄存器溢出，再考虑 Occupancy

    LDG STS

  2. 在SMEM上计算数据

  3. 数据从SMEM写回全局内存
    一个寄存器对SMEM的一次load 从寄存器到全局内存的一次store
    LDS STG

Memory Transaction 拆分机制：

float 访存（32 bit/线程）：一个 warp 访问 128 bytes，恰好一个 memory transaction
float2 访存（64 bit/线程）：一个 warp 访问 256 bytes，拆分为 2 个 memory transaction，每组 16 个线程（half-warp）
float4 访存（128 bit/线程）：一个 warp 访问 512 bytes，拆分为 4 个 memory transaction，每组 8 个线程（quarter-warp）

线程访问SMEM如何确定将要执行的内存事务的数量：

先确定单个线程访问SMEM的方式（float、float2、float4），接着用对应字节数乘以32得到1个warp要访问的字节数；
每次内存事务的字节数由该次事务阶段中实际被激活的 Bank 数量 × 单 Bank 宽度决定。
如果小于或等于128B，即1次内存事务的最大可处理字节数：warp的本次request仅需1个内存事务，无需拆分。同一warp的多个线程访问同一个Bank的不同地址，发生bank conflict，此时事务被拆分为多个事务阶段（phase/wave），每个阶段的划分遵循“tid 小优先”的原则，tid 小的冲突线程先占用 bank，tid 大的后移，且需保证每个 bank 最多服务一条请求；
如果大于128B：warp的本次request需1个以上的内存事务。同一warp中，处理同一内存事务的多个线程访问同一个Bank的不同地址，发生bank conflict，此时事务被拆分为多个事务阶段（phase/wave），每个阶段的划分遵循“tid 小优先”的原则，tid 小的冲突线程先占用 bank，tid 大的后移，且需保证每个 bank 最多服务一条请求；

为了尽量避免bank conflict，应让一共处理128B数据的线程在共享内存中尽量连续且对齐访问；

无冲突：32 个线程访问了 32 个互不相同的 Bank。硬件可以在 1 个时钟周期内 用 1 次内存事务 满足所有请求；
广播（Broadcast）：多个线程访问同一个 Bank 的同一个 32-bit Word 地址。硬件只从该 Bank 读取 1 次数据，并广播给所有目标线程，不增加额外的事务；
存储体冲突（bank conflict）：多个线程访问同一个 Bank 的不同 Word 地址。硬件无法在一个周期内同时从同一个 Bank 提取不同的数据，必须将这次 Warp 请求拆分为多个顺序执行的事务阶段（Phases / Waves）

线程块中：

不同warp内线程间的通信和同步：片上共享内存 on-chip shared memory 由__syncthreads()内部函数实现，该函数会阻塞线程块内的所有线程，直到所有线程都执行到该函数。

同一warp内线程间通信与同步：寄存器 shuffle原语

同一个Cluster内、不同线程块的线程间的通信和同步：分布式共享内存 Distributed Shared Memory

CUDA 编程模型要求线程块可以按任意顺序并行或串行执行

单指令多线程（Single Instruction, Multiple Threads, SIMT）是专门为GPU设计的并行计算模式。在统一的指令流控制下，多个线程在不同的数据上并行执行相同的操作
不使用__syncthreads()的情况下，warp之间的执行不保证同步
线程块之间的执行顺序不确定

当应用程序启动内核时，它会使用许多线程，通常是数百万个线程

一个线程块（Block）中的线程数量通常为32的倍数，最常见的大小为 128、256 或 512，最大1024
一个grid可能包含数百万个线程块，而执行该网格的GPU可能只有几十或几百个SM
CUDA 当前最多允许一个集群（Cluster）内有 8 个线程块

FLOP

  • FLOPs 算法、模型所需的浮点计算量总和

  • FLOPS 处理器硬件每秒可进行的浮点运算次数

  • FLOP/Byte 每读取、存入一个字节需执行的浮点运算次数，即任务的计算强度；数值越大，说明该任务越偏向于计算密集型；数值越小，说明越偏向于访存密集型（受限于内存带宽）
